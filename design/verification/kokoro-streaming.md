# Kokoro streaming web voice — 2026-10-07

**Correction after phone feedback:** These original checks established HTTP chunk delivery and client scheduling, but did not establish early upstream generation for a realistic reply. Later measurements showed a 28.5-second first-byte delay. The server now synthesizes short sections with bounded prefetch; see [the latency correction](scoop-streaming-latency.md) for timings and current behavior. Provider-native token streaming is not claimed.

- Web recipe read-aloud and voice preview now use OpenRouter model `hexgrad/kokoro-82m`, voice `af_heart`. Browser dictation still sends the final question automatically. Native voice adapters remain selected on native platforms; no native files or builds were changed in this task.
- `POST /api/speech` requires a signed-in session, the existing same-origin protection, 1–6,000 characters, and at most 20 calls per user per minute. It requests PCM with DeepInfra provider options `stream: true`, `sample_rate: 24000`. OpenRouter's speech API does not honor provider `order`/`only`, so no unsupported routing control was added.
- The server pipes upstream bytes into the response without collecting the full audio. `X-Accel-Buffering: no` disables nginx response buffering. It checks upstream HTTP status and PCM metadata without exposing upstream messages or credentials. A 90-second timeout and browser disconnection abort upstream work.
- The browser consumes signed 16-bit little-endian mono PCM at 24 kHz using Web Audio. It resumes audio within the initiating tap, keeps odd bytes across network chunks, schedules chunks in order, bounds queued playback, and waits for final playback before clearing the Stop button. Stop, reply switches, microphone input, chat close and page hiding cancel both fetch and scheduled audio. No device-speech fallback was added.
- `npm run check`: TypeScript and 320 tests passed. The nine new checks cover first audio before upstream EOF, signed PCM and odd-byte splits, playback completion, cancellation and late responses, bad/empty/truncated audio, capabilities, authentication, origin/text validation, raw response bytes and no-store headers.
- Deployment: healthy Compose container; deployed browser voice files and server speech adapter/route match workspace SHA-256 hashes. Public HTTPS `kokoro-voice.js` also matches local bytes.
- Activation completed on 2026-10-07: the authorized OpenRouter key is stored only in the git-ignored `.env` with mode 600. The Compose service was recreated, reports the key configured, is healthy, and the public HTTPS page responds 200. No credential value is included in verification output.
- Two real Kokoro `af_heart` requests returned successful PCM at 24 kHz mono. The first short request delivered 225,600 bytes (4.7 seconds audio), in 86 chunks; first audio arrived after 7.367 seconds and the response completed after 7.966 seconds. A subsequent signed-in request through the actual `/api/speech` route on the isolated QA server delivered 1,329,600 bytes (27.7 seconds audio), in 190 chunks. First bytes arrived at 2.300 seconds, before completion at 3.098 seconds; `X-Accel-Buffering` was `no`. The capabilities route reported `speaking: true`, voice `af_heart`. These are network measurements, not measurements of audible playback or guarantees of future latency.
